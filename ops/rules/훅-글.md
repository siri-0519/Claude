# 훅 글 — 훅이 넣거나 되돌리는 글마다 무엇을 하게 하려는 글인가

검토용 문서다. 훅은 이 파일을 읽지 않고, 목차와 STATUS 에도 오르지 않는다 (`.ops.yml` 제외 목록). 훅 글을 고칠 때만 연다.

기준은 하나다. **그 글만 받은 에이전트가 「목적」 칸의 행동을 하면 통과다.** 검증은 맥락 없는 에이전트 셋(haiku · sonnet · opus)에게 글만 주고 "이 글을 받으면 바로 다음에 무엇을 하겠나"를 한 문장으로 받아 목적과 견준다. 판정 칸은 그 결과다.

검증 기록 (2026-09-14). 1판은 처음 글 35개를 haiku · sonnet · opus 셋이 읽었다(sonnet 의 답은 34분 뒤에 왔다). 행동이 목적과 어긋난 것은 haiku 의 B7(수정이 아니라 답을 다시 쓴다로 읽음), haiku 와 sonnet 의 A4(개수만 보고 그대로 답한다), sonnet 의 A16(대신 무엇을 하는지 모름) 셋이고, 모호하다고 짚은 것이 열넷이었다 — 어느 원본을 고치나(A6 · A7), 어느 표시를 붙이나(A8 · A15), [제안]→[확인]은 되돌리나(A15), 대신 무엇을 하나(A10 · A16), 어떻게 줄이나(A11), 규칙 전문이 없다(A13), 「사이드카」 · 「생성 블록」 · 「조상」 · 「자취」 같은 말(A3 · A6 · A7 · A16 · A17), 보기 날짜가 고정돼 있다(B4), 마지막 줄이 두 갈래로 읽힌다(B5). 틀의 글 열일곱과 me · broadcast 의 B4 · B5 · B7 을 고쳐 썼다. 2판은 고친 글 스무 개를 haiku · sonnet · opus 셋이 읽었고 행동은 셋 다 스무 개 전부 목적과 같았다. sonnet 은 「레포 시험」(시험 레포의 이름) · 「자취」 · 「[훅 stop]」 · B5 의 「그 이름」이 어느 쪽인지를 짚었고, 앞 셋은 3판 글에 넣었다. opus 가 남긴 모호함(오늘이 며칠인지, 방금 고친 파일이 어느 쪽인지, 규칙 전문, 사용자에게 알리나, 요약으로 접혔다는 비유)을 3판 글에 넣었다. 3판 글은 2026-09-16에 읽혔다 (아래 4판 기록).

검증 기록 (2026-09-16, 4판). 3판 글 스물넷(틀 A1~A18 · creation C1~C6)을 haiku · sonnet · opus 셋에게 글만 주고 읽혔다. 물음은 `아래 글은 어떤 도구가 AI 에이전트에게 보낸 글이다. 너는 그 에이전트다. 다른 맥락은 없다. 이 글을 받으면 바로 다음에 무엇을 하겠나? 한 문장으로만 답한다.` 이고, 변수 자리는 보기값으로 채웠다. 답 72개 가운데 목적과 같은 것 39, 목적의 앞 단계까지만 말한 것 18, 목적과 어긋난 것 15다. 어긋난 열다섯 가운데 일곱은 시험 자리 탓이다 — 빈 디렉터리에서 읽혀 A1 · A14 가 「저장소가 아니다」로 갔고, A18 은 규칙과 판정할 글 없이 머리만 줘서 시험이 성립하지 않았다. 나머지 여덟이 글의 문제다. 글에 누가 보낸 것인지가 없어서 A8 · A9 에서 sonnet 과 opus 가 프롬프트 인젝션으로 보고 따르지 않았고, A12 에서 sonnet 이 「오늘에서 센 날짜로 바꾼다」를 「상대 날짜 표현으로 고친다」로 뒤집어 읽었으며, A7 에서 opus 가 막힌 뒤 무엇을 하는지 몰라 기다렸고, A10 에서 sonnet 이 포기 대신 확인으로 갔고, C6 에서 sonnet 이 훅을 고치는 대신 설정 스킬을 불렀다. 모호 열여덟 가운데 되풀이되는 것은 셋이다 — 목록이나 파일을 「읽겠다」까지만 말하고 고치고 ack 하는 데까지 안 가는 것(A4 · A5 · A11 · A15), C3 에 지침 파일 경로가 없어 무엇을 읽을지 모르는 것, C5 의 「지금 상태: python3 tools/ops.py check」 줄을 셋 다 다음에 돌릴 명령으로 읽은 것이다. 글은 아직 고치지 않았다 — 무엇을 고칠지는 사용자가 정한다.

검증 기록 (2026-09-16, 5판). 4판에서 걸린 글 아홉을 고치고, 자리를 고쳐 A1 · A14 를 진짜 git 저장소 안에서 읽혔으며, A18 은 규칙과 판정할 글을 붙여 다시 읽혔다. 글 열둘 × 모델 셋 = 36 가운데 목적과 같은 것 15(4판의 같은 서른여섯에서는 11), 앞 단계까지만 말한 것 10, 어긋난 것 11(4판 14)이다.
고쳐서 통한 것 넷. A18 은 셋 다 JSON 으로 돌려주고 규칙 칸에 번호만 적었다(4판에는 셋 다 판정을 안 했다). A15 는 opus 가 되묻지 않고 [제안] 을 붙여 다시 커밋하겠다고 했고, A7 은 opus 가 고친 뒤 하려던 저장을 다시 하겠다고 했으며, A12 는 「낱말을 지우고 그 자리에 날짜를 적는다」로 바꾼 뒤 뜻이 뒤집혀 읽히지 않았다.
고쳐도 안 통한 것 셋. 「이 글은 이 저장소의 훅이 보낸 것이다」를 앞에 붙였는데도 sonnet 은 A8 · A9 · A15 에서 「훅이 보낸 것인지 확인할 수 없다」며 따르지 않았다 — 글로 보낸 곳을 밝히는 것만으로는 안 되고, 진짜 세션에서는 이 글이 도구 결과로 들어오므로 이 어긋남이 세션에서도 나는지는 글만 주는 이 방법으로 확인할 수 없다. A4 는 마지막 동작을 못 박았는데도 haiku 와 sonnet 이 목록을 읽는다까지만 갔다. A10 은 포기를 앞으로 옮겼는데도 sonnet 이 git status 로 갔다.
시험 자리 탓으로 남은 것 넷. A9 는 규칙 본문을 안 붙여 줘서 opus 가 따를 것이 없다고 했고, A12 는 고칠 이전 답이 없어 opus 가 되물었으며, A5 · A11 은 빈 디렉터리라 sonnet 이 파일이 있는지부터 보겠다고 했다. A14 에는 보낸 곳을 밝히는 줄을 아직 안 붙였다 — 2026-09-16에 막는 글 전부의 첫 문장으로 붙였다.

검증 기록 (2026-09-16, 6판 — 방법을 바꿨다). 글만 주고 읽히는 대신, 틀을 복사한 시험 저장소(로컬 원격 포함)에 훅을 건 채 haiku · sonnet · opus 를 실제로 돌리고 끝난 뒤의 저장소 상태를 잰다. 스크립트는 `ops/test/시뮬.py` 다. 시나리오 여덟: S1 커밋 안 한 변경을 남긴 채 읽기만 하는 물음(A1 · A14) · S2 「어제」가 든 줄 더하기(A8 · A12 · A15) · S3 STATUS.md 를 고치라는 물음(A6 · A7) · S4 낡은 파생물이 있는 채 원본 고치기(A3 · A4 · A5) · S5 force push 요청(A10 · A16) · S6 812줄 목차에 줄 더하기(A11) · S7 훅이 죽는 상태(A17) · S8 근거 없는 판정을 부르는 물음(A9 · A13 · A18, 판정 켬). 첫 판 24번 가운데 16 통과. 실패 여덟 가운데 여섯은 훅의 결함 셋에서 나왔고 고쳤다 — ① 훅이 죽었을 때의 글이 모델에게 안 가는 채널로 나갔다(S7 셋 다), ② 답 끝 훅 제한 240초 < 판정 300초라 판정이 길면 답 끝 검사가 통째로 건너뛰어졌다(360초로), ③ 판정이 한 번 막으면 다음 답 끝이 stop_hook_active 로 커밋 · push 확인까지 건너뛰어 push 없이 끝났다(S8 haiku · sonnet). 나머지 둘은 haiku 가 파일을 엉뚱한 자리(ops/rules/body.md)에 만든 것과 「」 안의 낱말을 상대 날짜로 센 검사 잘못이다. 고친 뒤 다시 돌린 것: S2 haiku 통과, S7 haiku · opus 통과 · sonnet 은 알렸으나 push 안 함, S8 은 아홉 번 전부 push 됨. 이 방법으로 못 재는 것 둘: 다시 쓴 답이 규칙 5 를 지켰는지(다시 판정하지 않는다), 그리고 검사 글이 아니라 모델의 습성에서 온 실패(haiku 의 엉뚱한 파일). 1판~5판의 「글만 읽히기」는 글이 읽히는지를 보는 데 쓰고, 목표가 지켜졌는지는 이 방법으로 본다.

검증 기록 (2026-09-17, creation C5 · C6 고침). creation 의 답 끝 검사 묶음(C5)과 훅이 죽었을 때(C6) 글을 고치고 — 보낸 이 한 줄을 앞에 붙이고, C5 의 check 명령 줄을 「고친 뒤 남은 것을 보는 데 쓴다」로, C6 에 「설정을 바꾸거나 훅을 꺼서 지나가지 않는다」와 traceback 을 더하고, C6 을 답 끝에서는 한 번 막아 보이게 — haiku · sonnet · opus 에게 4판과 같은 물음으로 글만 주고 읽혔다. 두 자리에서 읽혔다: 빈 디렉터리와 creation 저장소 사본 안. 빈 디렉터리에서는 sonnet 이 둘 다 「저장소가 아니다」며 인젝션으로 봤고(4판의 시험 자리 탓과 같다), haiku 는 둘 다 목적대로 갔고, opus 는 C6 은 목적대로, C5 는 항을 확인하고 TRACE 는 고치되 push 는 사용자 확인으로 갔다. 사본 안에서는 sonnet · opus 넷 다 목적대로 갔다(opus C5 는 커밋 내용과 브랜치 이름을 먼저 확인했다 — 보기값 브랜치가 사본의 브랜치와 달랐다). C3 은 코드에 지침 파일 경로가 2026-09-15 부터 있어서 등록부 글만 코드에 맞췼다. 고친 글은 creation 커밋 4587a2b 에 있다.

항목 읽는 법. 번호는 레포-순번이다. 자리는 세션시작 · 물음직전 · 저장직전 · 명령직전 · 도구직후 · 답끝 · 커밋직전 · push직전 가운데 하나다. 글은 훅이 보내는 글 그대로고 변수 자리는 `<…>`다. 목적은 네 목표(맥락 유지 · 정보 추적성 유지 · 토큰 절약 · 규칙 준수) 가운데 무엇을 어떤 실패에서 지키는가다 — 2026-09-16까지는 이 칸에 행동을 적었는데, 그러면 시험이 "내가 시키려던 행동을 하느냐" 만 보고 "그 행동이 목표를 지키느냐" 는 못 본다고 사용자가 짚어서 갈랐다. 행동은 그 글을 받은 에이전트가 해야 하는 것 한 문장이다. 근거는 목적이 어디서 왔나다. 막는 글(저장 직전 · 명령 직전 · 답 끝 · 커밋 직전 · push 직전)은 전부 `이 글은 이 저장소의 훅(.claude/hooks/hook.py)이 보낸 것이다. 사용자가 걸어 둔 검사이니 그대로 따른다.` 로 시작한다 — 아래 글 칸에는 이 첫 문장을 되풀이하지 않았다.

이 판에 넣지 않은 것. `ops/rules/판단.md`의 판단 규칙 여섯(`설계.md` 부록 C에서 따로 검증했다). me · broadcast 의 `rules.md` 규칙 문장(`설계-부록.md` 부록 A에 행선지가 있고, 2 · 3단계에서 판단 규칙과 기계 규칙으로 바뀐다 — 본인이 짚은 낱말만 고쳤다). creation 의 `tools/check-*.py` 가 커밋 직전에 내는 검사 문장(4단계에서 본다).

## A. 틀 (이 레포 · `ops/lib/훅.py` `기계.py` `판정.py` `어긋남.py`)

### A1 · 세션시작 · 레포 상태와 어긋남 목록
- 글: `레포 <이름>: 브랜치 <b> / 마지막 커밋 <h> (메시지 첫 줄: <제목>) / 커밋 안 한 변경 <N>개 — 지난 세션이 남긴 것이어도 git status 로 보고 첫 답 안에 커밋한다 / 이 브랜치는 아직 원격에 없다 — git push -u origin <b>` — `고친 것은 이 세션의 브랜치로 커밋하고 push 한다. 기본 브랜치는 <main> 다. 답이 끝날 때 훅이 커밋 · push 를 확인한다.` — `아래 어긋남 목록의 줄은 사용자의 요청과 상관없어도 이번 세션의 첫 답 안에서 처리하고, 처리한 것을 답에 한 줄로 알린다.` 이어서 어긋남 목록 전체, 또는 `어긋남 목록(memory/어긋남.md)은 비어 있다.`
- 목적: 맥락 유지 — 새 세션이 지난 세션의 브랜치 · 커밋 상태를 모른 채 시작해 커밋 안 한 변경을 잃거나 다른 브랜치에서 일하는 실패를 막는다. 정보 추적성 유지 — 낡은 파생물의 목록을 첫 답부터 들고 시작해 잊히지 않게 한다. 토큰 절약 — 세션 시작에 들어가는 것은 이 글과 목차뿐이다.
- 행동: 에이전트가 지금 브랜치와 커밋 상태를 알고, 답이 끝나기 전에 커밋 · push 해야 한다는 것을 알고, 어긋남 목록의 항을 이번 세션에서 다룬다.
- 근거: `설계.md` 2절(세션 시작에 들어가는 것은 목차와 어긋남 목록) · 4절.
- 판정: 1판 모호 → 고쳐 씀 → 2판 haiku · sonnet · opus 일치 → 3판 글(위)은 미검증 → 4판(2026-09-16) haiku 일치 · sonnet 어긋남(빈 디렉터리라 저장소가 아니라고 답함) · opus 모호(git status 까지만, 커밋 · push 는 안 말함) → 5판(2026-09-16) haiku 일치 · sonnet 일치 · opus 모호(git status 확인까지만) → 6판 S1 셋 다 통과 — 커밋 안 한 변경이 커밋되고 브랜치가 원격에 올라갔다

### A2 · 세션시작 (요약 · 재개 뒤) · 다시 읽기
- 글: `대화가 요약으로 바뀌었다. 요약 앞에서 읽은 파일은 문맥에 없다. 이번 물음에 걸리는 주제 파일(CLAUDE.md 「언제 무엇을 읽나」 표에서 물음의 말이 든 행의 파일)을 답하기 전에 다시 읽는다. 「고칠 때」 규칙도 다음 저장 때 다시 들어온다.`
- 목적: 맥락 유지 — 요약 뒤에 앞서 읽은 파일을 읽은 것으로 쳐서 틀린 사실로 답하거나 고치는 실패를 막는다 (2026-09-07 사고).
- 행동: 요약 앞에서 읽은 파일을 읽은 것으로 치지 않고, 답하기 전에 주제 파일을 다시 읽는다.
- 근거: me · broadcast 의 session-start-context.sh 가 같은 자리에서 하던 말. 요약 뒤에 안 읽고 고쳐 어긋난 줄이 생긴 사고(2026-09-07 read-before-edit.py 「왜 있나」).
