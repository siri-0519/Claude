# ADR-0003 · kind는 6종을 유지하고, 분류의 무게는 라벨로 옮긴다

- 상태: accepted
- 일자: 2026-09-04

## 맥락

구조 검증에서 kind 6종의 문제가 두 가지로 정리됐다.

1. **배타성** — 한 파일은 kind를 하나만 가질 수 있다. 회의록에 결정이 적혀 있으면
   `record`와 `decision` 중 하나를 골라야 하고, 고르지 않은 쪽 검색에서는 사라진다.
2. **이중 진실원** — `kinds[].home`이 kind→디렉터리를, `ingest`의 `kind_by_dir`가
   디렉터리→kind를 매핑한다. 둘이 어긋나도 `ops check`는 통과한다(실증됨).

이에 대해 kind를 4종으로 줄이고 vault 디렉터리 분할을 없애자는 안을 제시했으나,
사용자가 다른 쪽을 택했다.

## 결정

**kind 6종은 그대로 두고, 실제 분류·검색의 주된 축은 라벨로 삼는다.**

kind는 "이게 대충 어떤 모양의 물건인가"를 나타내는 거친 한 칸으로 남는다.
"이게 무엇에 관한 것인가"는 라벨이 답한다. 라벨은 개수 제한이 없으므로
배타성 문제(1)는 라벨 층에서 해소된다 — 회의록은 `kind: record`이면서
`labels: [회의, 결정, proj-a]`를 가질 수 있다.

## 기각한 대안

- **kind를 4종으로 축소 + 디렉터리 분할 제거**: 제안했으나 채택되지 않았다.
  기존 kind에 이미 익숙해진 상태에서 종류를 줄이는 비용이, 그것이 푸는
  문제보다 크다는 판단.
- **kind를 다중값으로**: `kind`가 디렉터리를 결정하는 구조라 다중값이 되면
  파일이 어디 사는지가 정해지지 않는다. 라벨이 이미 다중값이므로 중복이기도 하다.

## 남는 것

배타성(1)은 라벨로 풀리지만, **이중 진실원(2)은 이 결정으로 풀리지 않는다.**
디렉터리와 `kind`는 여전히 같은 것을 두 군데서 말하고 있고, 어긋나도 아무도
잡지 않는다. 이건 별도로 다뤄야 한다 — 정합성 검사를 넣거나, 한쪽을 다른 쪽에서
파생시키거나.

"라벨로 올린다"가 코드에서 구체적으로 무엇을 바꾸는지도 아직 미정이다. 후보:

- `INDEX.md`를 kind로만 묶지 않고 라벨 축으로도 보여주기
- 라벨 오타·유사어가 갈라지는 것을 막을 장치(정규화 목록 또는 경고)
- `ops new`에서 라벨을 사실상 필수로 만들기 (지금은 선택)
- `ops check`에 kind↔디렉터리 정합성 검사 추가

어느 것을 할지는 실제 자료가 쌓인 뒤에 정한다. 지금 vault에는 아티팩트 2건,
파생 간선 0건뿐이라 라벨 체계를 미리 설계할 근거가 없다.
